# Durable cross-experiment lessons

- **Never pre-scale bf16 Q by a scalar via `cast→mul→cast` round-trip.** The bf16→fp32→bf16 truncates 7-bit mantissa and compounds over a 512-element dot × 32 topk blocks → abs_err ~3e-2. Apply scale post-dot on fp32 logits instead.
- Use **base-2 LSE** (`lse = m + log2(l)`); pre-multiply `sm_scale` by `log2e=1.4427` so logits come out in log2-space and softmax can use `exp2`.
- Latencies cluster into **small vs large** groups in our 128-workload set — always report split, not aggregate.
- `profile_baseline=False` in config → printed speedup is `0.00x` and reference latency is absent from output. For A/B, use `scripts/ab_benchmark.py`.
- **Split-K (flash-decoding) is the dominant structural win on small-num_tokens workloads.** 1 CTA per token leaves 147/148 SMs idle. Splitting TopK across NUM_SPLITS programs gave 4× speedup from exp_1 → exp_2.
- **NaN landmine in online softmax**: `exp2(-inf - -inf) = NaN`. Any kernel that runs a local online softmax over a subset that *might* be fully-masked (e.g. an all-padding split) must guard with `m_new_safe = tl.where(m_new == -inf, 0.0, m_new)` before `exp2(...)`, and `alpha = tl.where(m_prev == -inf, 0.0, exp2(m_prev - m_new_safe))`. Full-kernel softmax over the entire TopK didn't trip this because "all 2048 padded" is implausible in real workloads.
- **Triton globals must be `tl.constexpr`** inside `@triton.jit` functions. Cannot use a module-level `NEG_INF = float("-inf")` — declare it as `NEG_INF: tl.constexpr = float("-inf")` *inside* the kernel body.
- **A scalar-conditioned `if` in the hot loop defeats `num_stages=N` prefetching.** When body is gated by `if`, Triton can't issue async K/V loads for iter i+1 while computing iter i → workloads where the branch is always-true get slower. Keep compute unconditional; prefer `break` at end of iter, or mask with `tl.where` inside the tile ops. Measured: +25% regression on always-valid batched workloads in exp_3.
- **Workload characteristics** (from `experiments/workload_profile.md`, 2026-04-16): T∈{1,2,6,7,8}, max T=8; P=8462 constant; **median token uses only 33 of 2048 TopK entries**; 88% of tokens have >1024 padding; valid entries are contiguous with p50 contig-frac=1.0; unique pages per token p50=1. **Implication: the entire workload set is SM-starved (grid always ≤ 8 CTAs) and mostly padded** — split-K + padding-exit are the two structural wins.
- **NUM_SPLITS sweet spot is 8 for this problem (TOPK=2048, D_ckv=512, H=16).** Going from 8→16 regresses across the board (+33–50% in exp_4): combine-kernel cost grows linearly with splits (each split adds a 32-KB acc_si load + merge iter), and split-kernel per-CTA work drops to 2 BLOCK_N=64 blocks — too little to amortize prologue. Going higher needs a structurally different combine (tree reduce or grid-y parallel reduction).
- **`tl.static_range(N)` with large N (≥16) and per-iter work loading multi-KB tiles is a regression pitfall.** Triton inlines the entire body N times, blowing up register/icache pressure. Measured in exp_4: `static_range(16)` loading 32-KB acc_si per iter → 0.125 ms (5× worse than dynamic `range()`). Use dynamic `range()` with `num_stages>1` for such loops.
- **Triton doesn't support `break` inside `for` loops** (AST rejects it). For workload-adaptive early-exit, precompute a dynamic loop bound *before* the loop and use `range(0, dyn_upper, STEP)`. In exp_6, scanning `SPLIT_SIZE=256` indices once with `tl.sum((idx>=0).to(i32))` took ~1-2 µs (free on large workloads) and enabled −29 to −42% on T≤2 tokens, with compute fully unconditional inside the hot loop → `num_stages=2` pipelining intact.
- **Single-CTA combine/reduce kernels are classic serial bottlenecks.** Diagnosis: if combine time is flat across `num_warps ∈ {2,4,8,16}` AND flat across T, it's one-CTA-serialized. Fix: parallelize across any independent axis (in exp_7, D_ckv split across `grid2 = (T, D_CKV_SPLIT=4)`). Online-softmax's per-head state `[H] f32` can be replicated identically across D-programs at negligible compute cost (free). Guard the LSE write with `if d == 0:` to avoid store races. Measured: 12/12 A/B wins, −6% mean, projected cupti saving matched.
- **Fusing split+combine into a D-parallel single kernel is only a win for small T.** Each D-split CTA must load full D_ckv of K to compute `Q@K^T` logits (can't partition D on that dot), so 8 D-programs each do the full softmax → total work = NUM_D_SPLITS × split-design work. Exp_10 measured: T=1/T=2 wins 36–46% (launch-tax elimination + partial_acc round-trip saving dominates), but T≥6 regresses 2–3.5× (replicated compute dominates). Use hybrid dispatch: fused for small T, split+combine for large T. Per-regime specialization beats one-size-fits-all when workload characteristics differ sharply.
- **Host-level input-characteristic dispatch is free.** In exp_11, a single `if num_tokens <= 2:` branch on the host adds zero kernel overhead (one compiled variant loads per branch) while reclaiming the T≤2 launch-tax win from exp_10. Both variants are still Triton JIT kernels. Use this pattern whenever two distinct regimes in your workload distribution favor different kernel shapes.
- **Halving HBM byte volume doesn't help when the intermediate is L2-resident.** B200 has 126 MB L2. A short-lived back-to-back producer/consumer pair (like split→combine) keeps intermediates in L2. The memcpy-floor anchor from the profiler's HBM-resident measurement can overstate HBM-reduction headroom. Before doing dtype reduction, verify the bytes actually hit HBM (not L2) — e.g., by measuring achieved HBM bandwidth in isolation vs alongside the producer. Exp_12 measured: bf16 partial_acc (2 MB → 1 MB) regressed large-T by 3–10% due to cast overhead with no HBM saving.
- **Per-regime BLOCK_N specialization works when iter counts differ sharply.** In exp_13, halving BLOCK_N for the T≤2 path (BLOCK_N_FUSED=64) won −26% on workloads with valid ≤ 64 (single-iter kernels become half-work) but regressed +23% on a T=2 outlier with ~2000 valid (loop overhead dominates). Crossover: somewhere between valid=100 and valid=500. Split path (large-T) kept BLOCK_N=128 because large-T workloads cluster around higher valid counts and amortize the per-iter overhead well. Rule: tune BLOCK_N independently per dispatch branch when your workload distribution is bimodal.
- **Can't cheaply dispatch on `num_valid` from the host.** It's a per-token scalar only known on-device; a `.item()` round-trip or a preamble kernel would cost more than the saving. For per-workload BLOCK_N heuristics, either accept the tail regression or build an in-kernel adaptive path.
- **Atomic-barrier cross-CTA sync works in Triton for fusing two serial kernels into one launch.** Pattern: `atomic_add(+1, sem="release")` to signal, `while cnt < N: cnt = atomic_add(0, sem="acquire")` to wait, `atomic_add(-1, sem="release")` at end to reset for next call. Release/acquire pair carries memory-ordering of prior stores. End-of-kernel decrement relies on CUDA stream serialization — all decrements of call *i* complete before call *i+1* begins. Exp_15 saved ~2 µs of ~8 µs projected launch tax (-11% on large T, 10/12 A/B wins). Works as long as CTAs comfortably fit on available SMs (no risk of spin-wait deadlock).
- **Module-level counter cache (`dict[(device, num_tokens)] → zero-init tensor`) avoids `torch.zeros` per-call overhead**. Allocate lazily on first use; kernel's own decrement keeps it at 0 between calls. Critical for the atomic-barrier pattern to actually win — a fresh `torch.zeros` each call would cost ~5 µs, eating most of the saving.
- **Projected "launch tax" from `tl.event`-based profiles overstates recoverable savings.** Profile.md estimated 8 µs per collapsed launch; exp_15 recovered 2 µs. Some of the "launch tax" is unavoidable kernel dispatch that persists even with one kernel (grid-setup, CTA startup, memory allocation). Rule: when fusing to save launches, expect to recover ~25–50% of the profile's "launch tax" anchor, not the full number.
- **Serial accumulation via `tl.static_range(N)` outperforms 3D-load + `tl.sum(axis=0)` reduction for small N.** Exp_16 tried to replace the combine's unrolled 8-iter merge with a 3D `[NUM_SPLITS, H, BLOCK_D]` load + `tl.sum(axis=0)` → +19% regression on T=8. Compiler schedules the unrolled version with better ILP; vectorized 3D reduction adds cross-warp reduction ops and a full 32 KB intermediate. Threshold heuristic: `static_range(N)` is a win when `N × tile_bytes ≤ ~8 KB` per iter (small); regresses at ≥16-iter or 32-KB tiles (LESSON-13). At N=8 × 4 KB combines (this kernel), unrolled is the right choice.
- **For spin-wait polling on a shared counter, `tl.load(volatile=True)` beats `tl.atomic_add(0, sem="acquire")`.** `atom.add` with value=0 is still a PTX RMW that serialises through the L2 atomic unit when many CTAs poll the same line; `ld.volatile` is a pure L2 read with no RMW contention. Ordering is still guaranteed by the producer's `atomic_add(+1, sem="release")` — L2 is the coherence point on B200. Must add `tl.debug_barrier()` post-spin to block the compiler from speculating combine loads above the wait (HW ordering is still correct, only compiler-reordering is the hazard). Exp_18 saved ~0.15 µs per call on large T (A/B 9-10/12 wins). Recovers only ~10% of the profile's "spin bucket" — most of that bucket is wait-floor (slowest CTA), not per-iter poll cost.
- **num_warps=8 is a strict optimum for H=16 MLA kernels**, confirmed in both directions: num_warps=4 (exp_14, −3 to −5% regression, cross-head serialisation) and num_warps=16 (exp_17, +12.5% regression, 1-head-per-warp wastes MMA tile rows since MMA tile is [16, 16, 16] minimum). Don't sweep num_warps on this kernel shape unless MMA shape or H changes.
- **Triton 3.6's CTA clustering is INCOMPATIBLE with kernels using atomic cross-CTA synchronization.** `num_ctas=N` triggers the `TritonGPUPlanCTAPass` which asserts `!tiled` on each tensor op — the mixed atomic_add (barrier) + Q/K tile loads + softmax produces conflicting CTA-tiling decisions the planner can't resolve. Fails with `PlanCTA.cpp:212: Assertion !tiled failed`. Empirically ruled out for the current fused split+combine kernel shape. Also: Triton 3.6 on Modal does NOT expose `cluster_dims` — only `num_ctas` (driver hardcodes clusterDim.x = num_ctas, .y = 1, .z = 1). Any cluster plan must be axis-aware from the start. Verified on 2026-04-17 in exp_20 by probing `CUDAOptions.__dataclass_fields__`: missing `cluster_dims`; present: `launch_cooperative_grid`, `launch_pdl` (alternative cooperative primitives worth investigating next).
- **Manual `idx_scan`-before-Q reorder in small-T kernel is NEUTRAL.** Triton's `num_stages=2` prefetch already interleaves independent loads. Moving `idx_scan` earlier in the Python source does not change the PTX scheduling enough to move latency (exp_20 A/B: 8/12 B wins on *unchanged* large-T kernel → noise; small-T where change applies actually slightly regresses +0.2-0.4%). Load reorder is not a lever here.
- **`launch_pdl=True` alone is a no-op without upstream `griddepcontrol.launch_dependents` PTX.** PDL lets the next kernel start its prologue as the prior kernel finishes, but the prior kernel MUST explicitly emit `launch_dependents` at its tail. Triton doesn't auto-insert this even with `launch_pdl=True` — the kwarg only enables the capability, not the signal. Single-kernel benchmarks see no benefit; to get value, insert `tl.inline_asm_elementwise("griddepcontrol.launch_dependents;", ...)` at the kernel's epilogue so each iteration triggers the next. Even then, savings are ~1 µs of driver overlap, not the 5 µs noop floor (which is SM-dispatch time on the hardware, not driver dispatch). Verified exp_21.
- **Gluon `gl.dot_fma` is ~60–80× slower than `tl.dot` on B200** (exp_22: large-T median 1.30 ms vs exp_18's 0.016 ms). `dot_fma` is pure software FMA — no tensor cores. To get tensor-core throughput in Gluon you MUST use Blackwell primitives: `bw.tcgen05_mma` with tensor-memory descriptors (`bw.alloc_tmem`) and shared-memory staging. `dot_fma` is only a correctness scaffold, not a perf path.
- **`gl.dot_fma` requires `DotOperandLayout(op, parent, k_width=0)` with a `BlockedLayout` parent.** `k_width=0` is mandatory when parent is blocked ("ttg.dot_op kWidth parameter is not supported when the parent is a blocked layout"). Passing any other value (None, 1, 4, 8) errors. DotOperandLayout's `k_width` is a required positional argument — cannot be omitted.
- **`gl.dot_fma` operand dtypes must all match and match the accumulator's dtype.** Unlike `tl.dot`, the Gluon FMA op does not auto-upcast. Cast all operands to a common dtype via `.to(gl.float32)` BEFORE the `gl.convert_layout` to DotOperand. bf16 input is a subset of fp32 so the cast is lossless. `FMA.cpp aElem.getType() == tgtTy` asserts otherwise.
- **Gluon `warps_per_cta` must sum to the kernel's `num_warps`.** Can't under-allocate to match a small tensor's row count (e.g. H=16 with 8 warps forces `warps_per_cta=[8, 1]` even though only 1 warp per 2-row pair is needed — the same warp over-covers/replicates across rows). 1-D tensors use the full `warps_per_cta=[8]` with the same replication logic.
- **Gluon 1-D `gl.arange` layout must be a plain 1-D `BlockedLayout([x], [y], [z], [0])`** — not a `SliceLayout`-wrapped 2-D. Use `SliceLayout(axis, parent)` only when you're building an offset vector to broadcast INTO a 2-D tile (then index with `[:, None]` or `[None, :]`).
- **Gluon `gl.barrier` is listed in `language/__init__.py` but is NOT callable from inside a `gluon.jit` kernel.** AttributeError at JIT parse time. For cross-CTA sync, use `gl.atomic_add(ptr, 0, sem="acquire")` in a spin loop (same pattern as the Triton-side atomic barrier). For true within-CTA barriers in Gluon, only `bw.mbarrier` (Blackwell) is available — and it has its own setup (tmem/shmem allocation).
- **Gluon `gl.convert_layout` is the bridge between 1-D reduction results and the h_layout.** After `m_local = gl.max(logits, axis=1)`, the result inherits `SliceLayout(1, pn_layout)`. To combine with an `h_layout` tensor (e.g. running `m_i`), must `gl.convert_layout(m_local, h_layout)` first. Scalar-scalar ops across mismatched 1-D layouts error; this conversion is shmem-free if the distributions coincide.
- **Large `gl.dot_fma` shapes (e.g. 16x128x512) emit a `Large dot FMA instruction size may have slow compile times` warning.** First-call compile ~10–15 s on B200; cached in JIT cache after. Expect this on bring-up, not a bug.
- **Separate split + combine launches correctness-check a Gluon split kernel faster than a fused atomic-barrier version.** If the fused variant produces wrong output (exp_22 initial attempt: abs_err=4.52 on T=8), splitting into two independent launches isolates whether the bug is in barrier ordering or in the split-phase math. In exp_22 this refactor immediately passed — bug was barrier-related, not math-related.
- **Triton 3.6 cache_modifier accepts only `.ca` (default) and `.cg`; `.cs` is not exposed.** Attempting `cache_modifier=".cs"` fails at compile with `Cache modifier .cs not supported`. Use `.cg` for one-shot sparse-gather loads where L1 caching buys nothing.
- **`.cg` on K loads is regime-dependent.** In exp_23, `.cg` on kc/kp loads inside `_fused_split_combine_kernel` (large-T split, 8 CTAs co-occupying SMs) won 6/7 workloads by 0.02–0.18%. The same modifier on `_fused_attn_kernel`'s kc/kp loads (small-T, 8–16 CTAs total) REGRESSED 5/5 small-T workloads by 0.1–1.2%. Interpretation: L1 helps when grid is SM-starved and the same K lines could plausibly be re-touched across iter boundaries; L1 is pure overhead when grid is full and each CTA sees fresh K each iter. Apply cache modifiers per-kernel, not globally.
- **PDL is structurally invisible to CUPTI-based measurement.** Exp_25 confirmed: inline PTX `griddepcontrol.launch_dependents` + `launch_pdl=True` compiles and runs correctly on sm_100a, but A/B showed 6/12 wins (neutral/noise) because CUPTI measures each kernel's individual start/stop time — it can't see that the NEXT kernel's prologue is overlapping with the CURRENT kernel's tail. PDL's win is wall-clock between launches, not per-launch duration. Under the current CUPTI harness (mandated by CLAUDE.md "Cupti only measures CUDA runtime"), PDL is not a pursuable lever. This extends LESSON-29: exp_21's "no-op without signal" is only half the story — even with the signal, the measurement harness doesn't reward it.
- **Stride-partition (round-robin) beats block-partition for split-K load balancing when the valid prefix is short.** Block-partition `start = s * SPLIT_SIZE` concentrates work on few CTAs when `num_valid` is small; the barrier waits for the max-CTA. Strided partition `offs = s + arange(SPLIT_SIZE) * NUM_SPLITS` spreads prefix-valid entries evenly across all splits. The `num_valid`-based `max_bn = ceil(num_valid/BLOCK_N)*BLOCK_N` pattern still works because valid entries remain a contiguous prefix within each split's `idx_scan` (for prefix-valid input). Exp_26 recovered a reproducible -26% on one T=6 workload where max-per-token-valid ≈ 200-1000 (the regime where block-partition would need 2 iters but strided fits 1). Above valid ≈ 2000 strided introduces a small HBM-coalescing tax (~1% regression on large-T T=8 workloads): strided K-row gather fetches 128 KV rows at TopK-stride-8 vs contiguous TopK rows. Net win via outliers. Rule: stride-partition is a specialization for workloads with a medium-valid max token; safe to keep as default since workload distribution has median valid=33.
- **D-parallelism in the fused T≤2 kernel is load-bearing, not waste.** LESSON-16 described "replicated Q@K^T across D-parallel CTAs" as cost — interpretation matters. Exp_36 tested D_CKV_SPLIT_FUSED=1 (collapse 8 CTAs → 1 CTA per token). Result: uniform **+17-22% regression on all 5 T≤2 workloads** (T=1 +21%, T=2 +17-19%). Mechanism: (a) 8 parallel D-split CTAs share cached K via B200 L2 (126 MB) — the "redundant" Q@K^T compute is almost free, (b) 8-way parallel 2-KB output stores finish in ~1/8 the wall-clock of a single 16-KB store from one CTA, (c) 8 in-flight HBM K-loads overlap ~200 ns of latency that 1 CTA cannot hide. D_CKV_SPLIT axis is closed at 8 for the fused kernel; don't re-try this or nearby values (2, 4) — same structural cost.
- **Monotonic counter replaces reset-pattern atomic-barrier cheaply.** LESSON-21's atomic-barrier required a kernel-end `atomic_add(-1)` to reset the counter for the next call. Exp_37 replaced this with a host-side generation counter: target = gen × NUM_SPLITS, counter grows monotonically. Kernel spins on `count < target_count` (runtime arg). Saves one atomic RMW per CTA per call. Measured: **−2.5 to −3.6% on all 7 T≥3 workloads** (~0.44 µs saved per call). The decrement is pure bookkeeping, not load-bearing; removing it costs nothing. Int32 overflow safe for all realistic benchmark scopes (2B iterations ÷ gen_per_call = multi-year). Apply this pattern whenever a reset-based atomic barrier exists — monotonic is always preferable.
- **Per-slot atomics don't parallelize on B200 at either 32-B or 128-B stride.** Exp_38 (same-cache-line, 32-B total across 8 slots): +0.5-1.2% regression. Exp_42 (LESSON-45's explicitly-skipped variant — 128-B stride, one full cache line per slot): +0.9-1.4% regression on all 7 T≥3 workloads. Line-separation did NOT unlock observable L2 atomic-lane parallelism on this shape. Either (a) B200's L2 atomic unit has fewer than 8 lanes at cache-line granularity, (b) 8-way parallelism saves <250 ns vs the 8-wide vector load's extra cost, or (c) the monotonic spin's critical path is dominated by the slowest CTA's completion, not atomic throughput. The vectorized 8-wide spin-load + `tl.min` reduction costs ~3-5 ns per poll iter × ~70 iters/call = ~250-800 ns per call — a real tax that exceeds any producer-side parallelism gain. **Atomic-barrier axis is fully closed without a cluster-sync primitive** (Gluon `bw.mbarrier` with `num_ctas > 1` — structurally blocked by LESSON-27).
- **`eviction_policy` is a distinct load-side lever from `cache_modifier`.** `cache_modifier=".cg"` bypasses the L1 cache (L2-direct access); `eviction_policy="evict_first"` / `"evict_last"` / `"evict_normal"` is an L2 replacement hint telling the L2 which lines to evict first vs keep longer. These two kwargs compose orthogonally on the same `tl.load`. Exp_43: `evict_first` on one-shot K gathers in `_fused_split_combine_kernel` won 7/12 A/B (4/7 on affected T≥3 workloads) at mean Δ≈0; kept as a marginal win after 5 consecutive reverts (exp_38–42). **`evict_first` needs TWO conditions: (a) load is truly one-shot within the kernel AND (b) freed L2 capacity is meaningful (≥ tens of KB).** Exp_44 confirmed (a): applying `evict_first` to `idx_scan` regressed by +3.3–3.8% on T≥3 workloads because per-iter idx loads re-read the same scan data; evict-first marked them for eviction, KV-gather pressure evicted them, HBM refetch cost ~8 µs accumulated per call. Exp_45 confirmed (b): applying `evict_first` to per-iter `idx` alone (genuinely one-shot, condition (a) satisfied) still regressed +0.6–1.1% on 6/7 T≥3 workloads — per-iter load is only 512 B (128×int32 = 4 L2 lines), too small to free meaningful capacity; hint's instruction-level overhead dominates. Rule: before applying `evict_first`, verify (a) the tensor is read exactly once over the kernel's lifetime (not just once per iter — the SAME LINES must not be re-touched) AND (b) the freed capacity is ≥ tens of KB per CTA per iter. Safe targets in this kernel: K_ckv/K_pe gather (144 KB/iter per CTA, stride-partition guarantees row-disjoint). Unsafe by (a): `idx_scan` (re-read by loop), partial_m/l/acc stores that combine also loads. Unsafe by (b): per-iter `idx` (512 B too small). Unexplored complements worth trying: `evict_last` on Q_nope/Q_pe (multi-phase re-touched, dual hint, 16 KB Q_nope is meaningful) or on partial_m/l stores (multi-CTA-reader pattern).
- **Cache-modifier axis (`.cg`) fully closed after 4 sub-axes tested.** Four distinct tests exhausted the `cache_modifier=".cg"` lever: exp_23 on K_ckv/K_pe loads in split kernel (8/12 B wins, mean 0, kept for tiny direction-positive), exp_24 on partial_m/l/acc **stores** in split kernel (7/12, kept), exp_28 on combine phase partial **loads** (2/12 wins, **regression** — L1 tag check was overlapping with MMA compute, penalized when bypassed), exp_41 on Q_nope/Q_pe loads in split kernel (3/12 B wins, mean +0.0000, tie). The split-kernel Q tile (16 KB + 2 KB) is too small for L1 behavior to measurably differ from L2-direct. Rule: don't retry any `cache_modifier` placement on this kernel. When exploring this axis on a different kernel architecture, test sub-axes in priority order: K loads > partial stores > Q loads > combine loads (first three are zero-to-positive, last is negative).
- **Gluon `bw.tcgen05_mma` stage-1 is structurally uncompetitive at H=16.** Exp_40 ported exp_22's Gluon split scaffold with `gl.dot_fma` → `bw.tcgen05_mma`. Correctness 12/12 but latency 0.095 ms vs exp_37's 0.016 ms (6.1× regression). Root causes: (a) MMA minimum blockM=64 forces ≥75% phantom-row padding for H=16; the "more efficient" HM=128 tile requires D-chunking (4× MMAs per Q_nope logits) to fit in 232 KB SMEM, compounding to ~160 MMA-fences per call ≈ 80 µs; (b) persistent Q_nope at [HM=128, D_CKV=512] = 128 KB can't coexist with kc/kp/scratch buffers, forcing per-D-chunk HBM reload ≈ 16 µs; (c) TMEM `slice()` is last-dim only, so post-MMA row extraction needs an SMEM→register bridge. Stage 2 (`bw.mbarrier`) saves ~8 µs launch tax; stage 3 (cluster) saves ~17 µs Q+barrier — combined best-case end-of-stage-3 = 0.070 ms, still 4.4× exp_37. Triton `tl.dot` hides the same padding via its `wgmma` scheduler with no surfaced fence, giving ~5× framework-overhead advantage on this shape. **Gluon migration closed as a primary optimization axis unless a different kernel architecture (e.g. fusing N tokens across batch for larger effective blockM) is pursued.**
- **PTXAS rejects `cache_modifier=".cg"` + `eviction_policy="evict_last"` on stores.** Exp_46 compile error: 10 PTX store sites emitted `st.global.L1::evict_last.L2::cache_hint.cg.b*` and ptxas refused with "Modifier '.evict_last' cannot be combined with modifier '.cg'". Mechanism: Triton's `eviction_policy` maps to a PTX L1-eviction hint; `.cg` means "cache global in L2, bypass L1" — making the L1 hint undefined on that store. Asymmetric: on LOADS the combo IS legal (exp_43 kernel uses `.cg` + `evict_first` on K gather without issue). **Store-side L2 eviction hints are not user-programmable in PTX on Blackwell** — L2 replacement is HW-LRU only. Dropping `.cg` to enable `evict_last` would be a dual change and violates one-optimization-per-iter (LESSON-25). Rule: when adding eviction_policy to a store, either ensure no `.cg` is present or skip the hint. On loads, any combination is PTX-legal.
- **`input_precision="ieee"` is a no-op for bf16×bf16 `tl.dot` on Blackwell.** Exp_47 applied `input_precision="ieee"` to all 3 `tl.dot` calls in the combine kernel's split phase (Q_nope@K_ckv^T, Q_pe@K_pe^T, P@K_ckv). Correctness: abs_err byte-for-byte identical to default (1.56e-02 on both paths). A/B stride-2 runs: 8/12 then 7/12 B wins vs exp_43, mean Δ≈0 ms both — 15/24 B-win rate is only +1.5σ from noise null at sub-0.3% magnitudes. Mechanism: Triton's `input_precision` selects among FP32 MMA strategies (full IEEE / single TF32 / TF32x3 compensating). BF16 inputs bypass that selection — there's only one PTX instruction for bf16×bf16 → fp32 on sm_100 (`wgmma.bf16.bf16.f32`). **Axis closed for any kernel using bf16-only MMAs.** Also generalizes LESSON on marginal keeps: sub-1% direction-positive **without a mechanism story is noise, not signal** (contrast exp_43 which had L2-replacement mechanism predicting direction-positive). Keep requires (direction-positive + zero-cost + clean mechanism), not just statistical consistency.
- **`evict_last` on multi-reader cross-CTA shared loads is a winnable lever.** Exp_48 applied `evict_last` to Q_nope (16 KB) and Q_pe (2 KB) loads in split-combine kernel. Mechanism: 8 D-parallel CTAs for same token all load identical Q tiles; `evict_last` pins these lines in L2 for later-starting CTAs that would otherwise lose them to KV-gather eviction between CTA launch times. Result: 13/14 B wins on T≥3 affected workloads across 2 A/B runs (92.9%), mean Δ ≈ −0.35%. **Generalizes LESSON-48's two-condition rule to `evict_last`:** require (a) multi-reader pattern (same line read by ≥2 independent loads within kernel's lifetime) AND (b) enough footprint to measurably survive vs. default LRU (here 144 KB retained = 16 KB × 8 CTAs clearly worth it). Complementary to exp_43's `evict_first`: `evict_first` targets one-shot data ("get out fast"), `evict_last` targets multi-reader data ("stay"). **Critical measurement practice: stratify A/B results by affected vs unaffected workloads.** Exp_48 run 1 showed 11/12 B wins but T≤2 (fused kernel unchanged) all flipped to B — that was VM bias. Run 2's 6/12 aggregated masked the real signal (13/14 on T≥3 with T≤2 pure noise). Always split T-classes before judging keeps.

- **NUM_SPLITS axis re-opened by structural rewrites; "HBM-bound floor" projections are local optima, not global.** Exp_51 raised `NUM_SPLITS=8→16` (+ `D_CKV_SPLIT`, `BLOCK_D` coupled) and saw **6/6 T=7/8 workloads improve -15.8 to -19.5%** across 2 A/B runs (~2.7 µs absolute each) — the largest single-experiment delta since exp_37's monotonic counter. Profile.md claimed kernel was "within 1 µs of HBM-bound floor ~14.5 µs CUPTI," but that floor was computed at fixed NUM_SPLITS=8 byte volume. Doubling splits halves per-CTA bytes → per-CTA HBM latency drops → wall-clock halves on 2-iter tokens that become 1-iter. **When profile asserts "near HBM floor," ask "whose bytes?"** — the floor is NUM_SPLITS-dependent, and rewriting the partition structure moves the floor. Exp_4's historical NUM_SPLITS=16 regression pre-dated stride-partition (exp_26) AND monotonic counter (exp_37); those eliminated two reasons doubling splits was costly (block-partition straggler imbalance, per-CTA barrier decrement). Under modern structure, NUM_SPLITS=16 beats 8 on high-valid T≥6. **General rule:** after any structural rewrite (stride-partition, monotonic counter, fused launch), re-open tile-size axes that previously regressed. Also: **asymmetric-magnitude keeps are valid when win:loss ratio ≥ 5:1 on absolute µs** — exp_51 kept despite 1 regressing workload because 16.2 µs saved vs 1.6 µs lost on the affected population (not just "any regression = revert"). Regression itself = concrete follow-up (exp_52 = adaptive NUM_SPLITS per num_valid).
- **LESSON-13 refined: 32 KB static_range unroll is an UPPER bound, not the crossover.** Exp_52 tested `tl.static_range(16)` → `range(16)` on combine loop with BLOCK_D=32 (2 KB/iter × 16 iters = 32 KB unroll — right at LESSON-13's reported threshold). Result: **+5-7% regression on all 7 T≥3 workloads** (+0.7-0.9 µs combine slowdown). Mechanism: combine's per-iter body is small (1 load + softmax rescale + vector FMA ≈ 512 ops) and the softmax-rescale chain is a serial critical path. Static unroll enables 16-wide ILP by interleaving iter-i compute with iter-i+1 loads; Triton's `num_stages` auto-pipelining only prefetches 1-2 iters ahead. **At 32 KB unroll and below, `static_range` remains preferred even at 16 iters on this kernel.** Original exp_4 regression (0.125 ms) was at 32-KB-TILE × 16 iters = 512 KB of unrolled code, far past the threshold. **Rule: don't switch static→dynamic on unroll size alone** — also require (a) per-iter work large enough to mask sequential execution OR (b) irregular control flow that static unrolling can't statically schedule. Combine's regular dataflow violates both. Combine-loop unroll axis fully closed — remaining lever is structural tree reduction (parallelize the rescale chain across warps), not loop sugar.
- **Compiler-optimized online softmax patterns are hard to beat by semantic reformulation.** Exp_53 attempted three rewrites of combine: (A) `tl.reduce((m_bd, l_bd, acc_all), axis=0, combine_fn=_flash_combiner)` with m/l broadcast to 3D → +34-37% regression on all T≥3 (broadcasting makes per-step m/l work 32× larger; `tl.reduce` with custom combine_fn lowers to serial fold in Triton 3.6, not a tree); (B) offline softmax decomposition via `tl.max` + elementwise scale + `tl.sum((pacc_all * scale[:, :, None]), axis=0)` → +10% (32-KB `acc_weighted` materialization defeats the 2-KB rolling-tile register budget); (C) two-pass loop (pre-compute m_global via tl.max, then offline-scaled serial accumulate `l_global += l_si * scale_si; acc_comb += acc_si * scale_si`) → +20-25% (lost the ILP the compiler extracts from interleaved online-softmax alpha/beta + acc update, still serial write-back to l_global/acc_comb). **Rule:** when the profile recommends "tree reduction" to break a serial chain, profile's savings estimate ASSUMES the compiler can't already parallelize the static-unrolled chain. In practice, Triton's `static_range(N)` + online-softmax pattern gets significant cross-iter ILP because independent parts of iter N+1 (exp2 for alpha/beta on different operand) can schedule alongside iter N's accumulation. Any reformulation that blows up intermediate tile size (broadcast, materialize temp) tanks performance. **To genuinely parallelize the rescale chain, you need structural rewrites:** (i) warp-level split (each warp processes N/8 partials independently, then shmem-barrier cross-warp reduce), (ii) multi-kernel tree (16→4→1 across kernel launches with atomic barriers), (iii) NUM_SPLITS reduction + change critical path length. Single-kernel tl.reduce or offline decomposition does not qualify. Combine axis fully closed across exp_4, exp_5, exp_52, exp_53 — four distinct angles tried.
- **Host-side adaptive NUM_SPLITS dispatch via `.item()` is catastrophic, and per-T dispatch can't target per-workload data-dependent regimes.** Exp_54 attempted to recover exp_51's 4c46a94b regression (+14%, 1.6 µs lost / call) via adaptive NUM_SPLITS. **Variant A (Action 1, valid_max .item()):** `valid_max = int((sparse_indices >= 0).sum(dim=-1).amax().item())` then dispatch NUM_SPLITS=16 vs 8 on `> 1024`. Result: **0.013 ms → 0.103 ms on 2207f0fd (~9× regression)** — pure latency explosion from host-device sync. CUPTI DOES measure this because the sync serializes the GPU queue; even if CUPTI records only kernel duration, the target kernel ends up waiting behind the sum+amax kernels and the memcpy-to-host. Adds 3 Torch kernel launches + 1 sync + 1 memcpy ≈ 80-100 µs per call on a 12-µs workload. **Variant B (Action 2, T-based fallback):** plan.md asserted 4c46a94b was T=6 — FALSE. workload_profile.md line 89 shows `4c46a94b: T=8, valid_max=1002`. With T-based rule `num_tokens >= 7 → NS=16`, 4c46a94b at T=8 still routes to NS=16 (same as exp_51, no change). Only T=6 workloads (3 of 23, not sampled by stride-2) switched to NS=8; stride-2 mean Δ = -0.0000 ms confirmed neutral. **Rule:** (1) `.item()` in a kernel launcher hot path is NEVER free, even on "cheap" reductions — the sync point serializes with any in-flight GPU work and adds tens of µs.
